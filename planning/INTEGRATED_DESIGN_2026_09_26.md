## 2. 設計原則（21日版へ伸ばせるMVPにするための10原則）

1. **数値はコードではなくキャンペーン設定に置く。** 7日版・21日版・難度違いは設定ファイルの差にする。
2. **日番号で分岐しない。** `day_count == 1` のような判定を新しく書かない。日ごとの例外は設定の「日別上書き」で表す。
3. **朝に一度決めて、その日は使い回す。** 客・人数・予報・相場は朝の計画（DayPlan）に固定し、表示の開閉や再読込で再抽選しない。予報は計画から作る＝予報と実際が矛盾しない。
4. **販売の成立と、料理の評価を分ける。** 未完成の料理は売れない（経済の問題）。完成した料理の出来はBAD〜GREATで評価する（品質の問題）。
5. **料理の出来と、人との関係を分ける。** 出来は評判・売上へ、関係は「次回へ残す事実」へ。GREATでしか手に入らない必須情報を作らない。
6. **会計は帳簿から導く。** 予算表示・前日成績・最終成績・（21日版の）投資回収を同じ記録から計算する。
7. **必須情報は抽選・料理の成否・売り切れに依存させない。**（【7日表】§11を継承）
8. **常連の基本の好みは変えない。変化は「今日の頼み」として明示する。**
9. **乱数を用途ごとに分ける。** 需要・客の抽選と、反応文の抽選を別の乱数にする（同じ朝からの再挑戦を同じ抽選にするため）。
10. **汎用エンジンを先に作らない。** 作る土台は§4の7部品だけ。21日版で要る機能の実装はしない。

## 4. 拡張性の土台（MVPで作る7つの部品）

21日版の機能は作らない。21日版で「作り直し」にならないための形だけを、MVPの必須項目の実装と同時に入れる。状態は `GameState` のフィールドに置き、処理は `Day1Events`・`Ingredients` と同じ小さな静的クラスに置く（既存の決定「GameStateの分割はしない」「汎用会話エンジンは作らない」を守る）。

### 4.1 データ構成

  schedules/week7_regulars.json # 常連の固定枠（日×時間帯）
  schedules/mob_rules.json      # モブの抽選ルール（既定＋日別の上書き）

### 4.3 F2：その日の計画（DayPlan）

WAKEで1回だけ作り、その日の間は使い回す。今の `DebugPanel._tonight_schedule` と `Day1Events._mob_instances`（静的変数）をここへ移し、UIとデータ部品の隠れた結合をなくす。

```
DayPlan {
  day, seed                      # seed = run_seed * 1000 + day（【試遊】と同じ規則）
  demand_center, demand_actual   # 需要の中心と、実際に引いた値
  slots: [ { name, regular_id, episode_id, today_request,
             mobs: [ { instance_id, type, count } ] } ]
  forecast                       # 表示用。§3.2 M-I02の精度で planから作る
  bills_due                      # 今日確保する支払い
  # 21日版で追加：market（相場・閉店）、events（混雑予告）、accept_cap（受付上限）、policy（看板料理）
}
```

- 乱数は `RandomNumberGenerator` をDayPlan専用に持つ。反応文の抽選は別の乱数（原則9）。
- **予報の幅は `demand_center` を基準に出す**。`demand_actual` を中心に幅を出すと、真ん中の値＝実際の値と読めてしまう。モブは種類の一覧（重複除去）だけを出し、組数は出さない（組数から人数が逆算できるため）。
- デバッグのモブ人数上書きは「計画を作り直す」操作として残す。

### 4.4 F3：販売判定と品質判定（SaleRule／判定v2）

```
SaleRule.check(bowl, soup, order) -> { ok: bool, reasons: [NO_FLAVOR, NO_TOPPING, STRENGTH_ZERO, SHORT_SERVINGS] }
Judge.grade(bowl, soup, order, favorite_known) -> { grade, base_grade, penalties: [...], favorite_hit }
```

- 名前あり客・団体（1/2レシピ）・持ち帰りの全経路が、材料・鍋・現金を動かす前に `SaleRule.check` を呼ぶ。今の `_serve_customer()`・`_apply_mob_recipe()` に散っている条件をここへ集める。
- `order` は「基本注文＋今日の頼み」を合成した実効注文。判定は実効注文で行う。
- `penalty_stacking` の切り替えを設定から読む（MVPはfalse）。

### 4.5 F4：帳簿（Ledger）

```
LedgerEntry { day, phase, category, amount, item?, count?, unit_price?, ref? }
category: daily_cost / rent / water / kit / prep / market / dashi / sale / fund / refund
          （21日版で追加：equipment / gift / upkeep）
```

- 予算表示（残金・確保・使える額）、前日成績v2（使用原価・廃棄原価・在庫評価）、Day7結果、21日版の設備回収（増分利益）を、すべてここから計算する。
- 在庫ロットの購入単価（現行の `perishable_batches`）と組み合わせて使用原価を出す。
- 既存の日次ログ `user://balance_log.jsonl` は帳簿の日次集計として出力し直す（自動試遊の比較が続けられる）。

### 4.6 F5：来店記録（CustomerMemory）

現行の `known_favorites` を置き換える。7日間を通して残し、新しい周で消す。

```
memory[customer_id] = {
  favorite_known: bool,
  visits: [ { day, slot, served: bool, grade, ingredients, request_honored, choices } ],
  facts: { "takeout_recipient_known": true, "camera": "pot_only", ... },  # 次回へ残す事実（1場面1〜2個まで）
  seen_episodes: [ ... ]

```

好感度のような数値は持たない（【ADV】の方針）。「何を出したか」「何を選んだか」「何を約束したか」の事実だけを残し、台詞の分岐はそれを読む。

### 4.7 F6：来店場面（Episode）と選び方

```json
{
  "id": "delivery_man_02",
  "customer": "delivery_man",
  "requires": { "facts": { "takeout_recipient_known": false }, "not_seen": true },
  "order": { "today_request": { "tags": ["MELLOW", "GENTLE"], "servings": 1, "label": "持ち帰り" } },
  "callback": { "last_grade_good_or_better": ["昨日の、あいつが残さず食べた"],
                "last_grade_bad": ["昨日のは……まあいい"] },
  "pre_order": ["…"],
  "reaction": { "GREAT": ["…"], "GOOD": ["…"], "OK": ["…"], "BAD": ["…"], "UNSERVED": ["…"] },
  "body": ["…"],
  "choices": [ { "id": "message", "options": [
      { "label": "預かる", "set": { "holding_message": true } },
      { "label": "本人に言ってくれ", "set": { "holding_message": false } } ] } ],
  "closing": { "default": ["…"] },
  "sets_facts": { "takeout_recipient_known": true },
  "must_info": []
}
```

- **選び方**：DayPlanを作るとき、その枠の常連について「前提を満たす未読の場面」を1つ選ぶ。無ければ短い近況の場面に落とす（同じ長話を二度出さない）。
- **後半は結果が出てから組む**：`reaction`・`closing` は提供（REACT）の後に、実際の出来・選択を見てイベント列に足す。来店時点で最後まで固定すると、今回の選択が反映できないため（【ADV】§4末尾）。
- `must_info` を持つ場面は、売り切れ・断る・早仕舞いでも `UNSERVED` 版で再生する。
- 既存の `EventRunner` に条件分岐を持ち込まない（「データと処理の分離」を維持）。組み立ては選ぶ側で行う。

### 4.8 F7：朝の保存と再挑戦（RunSnapshot）

- WAKEの運営費を引く**前**に、`GameState` の全状態（所持金・在庫ロット・評判・来店記録・帳簿・日数）とDayPlanを辞書に保存する（メモリ内）。
- 再挑戦はこの辞書から復元するだけ。DayPlanも同じものを使うので抽選は変わらない。
- `GameState.to_dict()/from_dict()` を作っておけば、フェーズ4の1枠セーブ（既存の決定）も、21日版の日次セーブ・複数スロットも、この辞書をファイルへ書き出す処理を足すだけになる。
- Day7の結果表示のため `Phase.RESULT` を追加する。`FlowController.advance_phase()` の「最終日なら `reset_for_new_game()`」を「最終日ならRESULTへ」に変える。

## 7. 検証計画

### 7.1 自動試遊（段階3で実施。【試遊】の仕組みをそのまま使う）

比較する方針：空料理（→売れないことの確認）、安い完成料理だけ、基本GOOD、既知好物あり、初回から好物を狙う、仕込み過少／過大、団体の分割、濃さ・鮮度のミス、1組を断る、修繕基金に積む。

仮の合格ライン（推奨値を確定するための基準で、面白さの証明ではない）：

- 基本GOODの平均最終現金が1500〜1700。1500達成率が85〜95%。
- 安い完成料理だけ・注文無視の方針が、現金・品質・常連実績の**すべて**で基本GOODを上回らない。
- 品質失敗2件（個人1杯＋団体1組）でも7日間の営業を続けられる。
- 小仕込み固定の早期閉店が「供給不足の学び」として起きるが、資金不足休業は0。

### 7.2 人の試遊（段階6。5人程度）

- Day3までに「仕入れを変えた理由」を説明できる人が4人以上。
- 二度目の来店で「前の料理を覚えている」と自分から気づくか。
- 料理の正解タグ以外に、その人の事情を1つ説明できるか。
- BADを出したとき、続きが気になって進めるか、ロードしたくなるか。
- 1〜2回の失敗からDay7まで営業を続けられるか。
- 事件の真相が分からなくても、最後に「何が変わったか」を1つ挙げられるか。

## 8. 決定事項（2026-09-26 しまさん承認・8項目とも推奨案で確定）

| # | 論点 | 決定 | 採らなかった案 | 理由 |
|---|---|---|---|---|
| 1 | Day1の杯数と初期在庫 | **9杯＋有料初日セット210＋無料在庫0** | 現行（13杯＋無料在庫を増量したまま） | 儲かりすぎの主因がDay1。定数・予報・テストを1つの値に揃えられる。前回の増量は戻すことになる |
| 2 | 常連の来店 | **7日版は21枠固定**（§3.8） | 現行の抽選を維持し、約束の相手だけ優先配置 | 全員の「その後」を保証でき、会話の執筆量も見積もれる。抽選の変化はモブで残る |
| 3 | 予報の精度 | **Day1は完全公開、Day2以降は総杯数の幅（中心±1）** | 現行の正確な人数表示 | 仕入れに「読み」が残る。幅の出し方は§4.3の注意どおり |
| 4 | 初回の好物 | **表示は隠し、入れれば初回でもGREAT** | 現行（既知になるまで判定に使わない） | 会話のヒントから好物を拾えたことが報われる |
| 5 | 減点の重ね掛け | **MVPは合計1段階＋事前表示** | 個別に1段階ずつ | 実測は現行ルール。変更要因を減らす |
| 6 | 資金不足のゲームオーバー | **残す＋同じ朝から再挑戦** | ソフトフェイル（休業して翌日へ） | 緊張感を残しつつ、1回のミスで7日分を失わせない |
| 7 | 修繕基金とおごり | **修繕基金はMVP（段階6）、おごりは21日版** | 両方MVP／両方21日版 | 基金は結果画面の目標と直結。おごりは物語の常連が揃ってから効く |
| 8 | 鍋の同時容量 | **14（水は残量12以下）** | 同時18を許して「同時容量」の概念を持たない | 給水のタイミングに判断が生まれる。総供給は同じ |
