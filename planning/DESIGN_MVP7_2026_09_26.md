### 10.3 経済・ルール（確定）

#### 10.3.1 販売成立条件（SaleRule）

提供できる椀の条件（すべて満たす）：

```
味の素材が1つ以上（HOT/MELLOW/SOUR/BITTER/SAVORY のいずれかを持つ素材）
具の素材が1つ以上（Ingredients.is_topping() が true の素材）
鍋の濃さが 1〜5（0 は提供不可。既存どおり）
鍋の残量が、その提供の杯数以上
```

- 名前あり客・団体の1/2レシピ（`_apply_mob_recipe()`）・持ち帰りの**全経路で共通**。
- 判定は、在庫・鍋・現金を動かす**前**に行う。満たさなければ何も動かさず、欠けている理由（「味が入っていない」「具が入っていない」など）を表示する。
- 「具なしの椀は常にBAD」（フェーズ1で実装済み）は、この条件により「具なしの椀は売れない」に置き換わる。
- **BADの返金はしない**。完成した料理の出来が悪いことは評判で罰する（全額返金は品質失敗2件で1500達成率が49.2%→0.6%に急落するため不採用）。

#### 10.3.2 判定ルールv2

```
一致数 = 椀の素材のtags と 実効注文の要求tags の一致数（数え方は既存どおり）
実効注文 = 客の基本注文（いつもの）に「今日の頼み」があれば上書きしたもの（10.5.2）

  0個            → BAD
  1個            → OK
  2個            → GOOD
  2個＋好物あり  → GREAT   ※好物は2軸がそろったときだけ効く（1個＋好物はOKのまま）

減点：濃さが1か5、または傷んだ素材を使った → 1段階下げる（両方でも1段階。既存どおり）
好物：表示は既知になるまで隠す。判定には初回から使う（入れていればGREATになる）
```

- 提供前に「このままだと1段階下がる：濃さ1」の形で減点の理由を表示する。
- 減点の重ね掛け（各1段階）はキャンペーン設定の `penalty_stacking` で切り替えられる形にし、7日版は `false`。
- 好物を既知にするタイミング（`mark_favorite_known`）は既存どおり「判定に使われる来店を終えたとき」。

#### 10.5.2 注文カード＝「いつもの」＋「今日の頼み」

- 常連の基本注文は不変。7日間で2〜3場面だけ、客が今回の頼みを明示する（例：配達員の持ち帰り）。
- 注文カードには「いつもの：HOT＋POWER／今日：MELLOW＋GENTLE」のように両方を残す。会話を飛ばしてもカードで分かる。
- 聞き直し（確認）の操作を用意する。聞き直しても料金・評判・関係は下がらない。確認操作そのものを正解フラグにしない。
- 今日の頼みは、その日に買える基本素材で必ず応えられるものに限る。初登場の高級素材を購入後に突然要求しない。

#### 10.5.3 会話の構成

```

提供後: 料理への短い反応（出来4段階＋未提供）
        共通本文（食事中の話。場面の重心はここ）
        締め（選択・約束に応じた短い差分）
```

- 評価4段階ぶんの長文を書かない。長い本文は1本で、差分は冒頭2行・反応・締めだけ。
- GREAT専用の枝には小さな私事だけを置く。火災の手掛かりなど必須情報を置かない。
- 謝罪などで料理の評価は変えない（謝れば損失が消える仕様にしない）。わざと失敗すると親密になる経路も作らない。
- 執筆の目安（読み時間の実測ではない）：来店・注文25%、一口目15%、食事中の話50%、去り際10%。
- 読む時間で鍋の煮詰まり・腐敗・客の待ちを進めない（現行どおりターン制）。

#### 10.5.4 店主の距離感の選択（3〜4件）

- 例：配信者の撮影（鍋だけならいい／今夜は撮影なし）、伝言（預かる／本人に言ってほしい）、踏み込んだ話（今は聞く／食べている間は置いておく）。
- 二択で十分。善悪点にせず、次回の姿や台詞に残す（撮らせたら次回は映像を見せてくれる／撮らせなければカメラを鞄に入れたまま来る）。
- 断ったことで説明のない大きな罰が起きる分岐は作らない。

#### 10.5.5 ニュースと会話の分担、必須情報

- ニュース＝街の変化（検問で道が通れない、映像が出回っている、港が封鎖された）。会話＝その人に起きたこと（遠回りで休憩を失った、自分の映像を見返せない、仕事に戻れない）。
- 必須情報9項目（SEVEN_DAY_OUTLINE §11）はニュースと固定場面で必ず出す。場面データの `must_info` で印を付け、売り切れ・断る・早仕舞いでも「未提供」版で再生する。
- 「搬出があった」（観測）と「誰が何のために運んだか」（解釈）を分ける。客の発言を客観的事実へ自動で昇格させない。

#### 10.5.6 人物表と一晩の配分

- 各常連に「今日欲しいもの／自分で決めたいこと／譲れない一線／話し方」を1行ずつ書く。夜の女は本人が名乗る名前に切り替える。
- 1晩の3人を、原則「事件を動かす話」「暮らしへの影響」「事件と関係ない私事」に振り分ける。

#### 10.5.7 結末と同席

- 個人的な結末を1本閉じる（例：配達員の持ち帰り先が、終盤に「今度は一緒に来る」）。
- Day7老婆の締めは全周共通の短い場面＋実際の接客を受けた一言の差分。対応する出来事を見ていない周へ機械的に流さない。失敗した周にも「明日も開けるんだろう」のような、やり直しの余地を残す結びを置く。
- Day5の宵の口→夜半の境目で、チンピラと新人警官の短い同席（4〜6行）。注文・会計は1人ずつのまま。

#### 10.5.8 最初の試作（本文を全部書く前に）

配達員の3場面（初来店で「いつもの」と持ち帰りの頼みが違う／再来店で前回の料理に2行で返す／締めで成功・失敗どちらにも関係が続く）＋配信者の撮影の選択1場面。料理の成功・失敗×確認した・しなかったの4条件で読み比べる。

### 10.6 周回・終了（確定）

- **結果画面**：`Phase.RESULT` を追加する。`FlowController.advance_phase()` の「最終日なら `reset_for_new_game()`」を「最終日ならRESULTへ」に変える。表示は「街で起きたこと」「客との間に残ったこと」「店の成績（現金＋修繕額・GOOD以上率・常連GREAT回数・未提供・廃棄）」。選択肢は「もう一度（同じ周をDay1から）／新しい周／終わる」。料理成績を人間関係の善悪や真エンド条件にしない。
- **同じ朝からの再挑戦**：GAME_OVERと結果画面から、その日の朝（同じDayPlan＝同じ抽選）へ戻って仕入れからやり直せる。抽選を引き直す手段にはしない。
- **1枠セーブ**（既存の決定・フェーズ4）：朝の保存（10.8.6）と同じ辞書をファイルに書く。調理中・会話途中は保存しない。
- **目標の表示**：完走（7日営業）／標準：現金＋修繕額1500／挑戦：1600／料理：全需要の85%以上にGOOD以上／常連：GREAT 8回以上。未達でも物語や続きのプレイを失わない。

### 10.7 修繕基金（確定・フェーズ4の後半）

- 任意で積み立てる。累計150で手書き看板、300で棚と雨よけ、600で屋台を自分の名義に。見た目と営業記録が変わる。
- 返金不可。仕入れと同じ現金を使う＝「今日入れるか、明日の仕入れに回すか」の判断になる。
- 売上を恒久的に増やす効果は付けない。目標判定は「現金＋支払済み修繕額」（投資したせいで現金目標が不利にならない）。

|---|---|---|---|---|---|
| F1 | キャンペーン設定 | `data/campaigns/week7.json` | `Rules`（静的） | 数値・徴収日・Day1の上書き・目標 | 週構成・定期支払い・難度（X-01, X-05, X-15） |

#### 10.8.2 F2 その日の計画（DayPlan）

WAKEで1回だけ作り、その日の間は使い回す。今の `DebugPanel._tonight_schedule` と `Day1Events._mob_instances`（静的変数）をここへ移す。

```
DayPlan {
  day, seed                      # seed = run_seed * 1000 + day
  demand_center, demand_actual
  slots: [ { name, regular_id, episode_id, today_request,
             mobs: [ { instance_id, type, count } ] } ]
  forecast                       # 表示用。10.4の精度でplanから作る
  bills_due                      # 今日確保する支払い
}
```

- 乱数はDayPlan専用の `RandomNumberGenerator`（seedから作る）。反応文の抽選は別の乱数。
- `OpenController` はDayPlanの `slots` から作る（今の `customer_schedule()` の戻り値と同じ形を保つ）。
- デバッグのモブ人数上書きは「計画を作り直す」操作として残す。
- 21日版で足すフィールド（`accept_cap`・`market`・`events`・`policy`）は**今は作らない**。

#### 10.8.3 F3 販売判定・品質判定

```
SaleRule.check(bowl, soup, order) -> { ok: bool, reasons: [NO_FLAVOR, NO_TOPPING, STRENGTH_ZERO, SHORT_SERVINGS] }
Judge.grade(bowl, soup, order) -> { grade, base_grade, penalties: [...], favorite_hit: bool }
```

- 今の `_serve_customer()`・`_apply_mob_recipe()` に散っている条件を `SaleRule` に集める。
- `OpenController.judge_bowl()` は `Judge.grade()` を呼ぶ形にし、既存の `current_bowl` への記録（`penalty_strength` 等）は保つ。
- `order` は基本注文と今日の頼みを合成した実効注文。

#### 10.8.4 F4 帳簿

```
LedgerEntry { day, phase, category, amount, item?, count?, unit_price?, ref? }
category（7日版）: daily_cost / rent / water / kit / prep / market / dashi / sale / fund / reserve / release
```

- 予算表示（残金・確保・使える額）、前日成績v2、結果画面は、すべて帳簿から計算する。
- 使用原価は、在庫ロットの購入単価（既存の `perishable_batches`）から出す。
- 既存の日次ログ `user://balance_log.jsonl` は帳簿の日次集計として出力し直す（自動試遊の比較を続けられる形を保つ）。
- 21日版のカテゴリ（`equipment`・`gift`・`upkeep`）は今は作らない。

#### 10.8.5 F5 来店記録

既存の `known_favorites` を置き換える。7日間を通して残し、新しい周で消す。

```
customer_memory[customer_id] = {
  favorite_known: bool,
  visits: [ { day, slot, served, grade, ingredients, request_honored, choices } ],
  facts: { ... },          # 次回へ残す事実（1場面につき1〜2個まで）
  seen_episodes: [ ... ]
}
```

好感度のような数値は持たない。「何を出したか」「何を選んだか」「何を約束したか」の事実だけを残し、台詞の分岐はそれを読む。

- 組み立ては選ぶ側で行い、`EventRunner` に条件分岐を持ち込まない。

#### 10.8.7 F7 朝の保存と再挑戦

- WAKEの運営費を引く**前**に、GameStateの全状態（所持金・在庫ロット・だし・評判・来店記録・帳簿・日数）とDayPlanを `to_dict()` で辞書にする。
- 再挑戦はこの辞書を `from_dict()` するだけ。DayPlanも同じなので抽選は変わらない。
- フェーズ4の1枠セーブは、この辞書をファイルに書く処理を足すだけにする。
