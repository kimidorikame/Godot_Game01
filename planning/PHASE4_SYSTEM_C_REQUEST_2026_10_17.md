規模が大きいので、次の2回に分ける案を基本とする。**planで、分ける／分けない／別の分け方、のどれにするかを推奨付きで示すこと**。

| 案 | 内容 | 狙い |

| **C1** | 提供後の骨格：`UNSERVED`の反応・`body`・`closing`（`default`のみ）・`pre_order`・`must_info`の未提供版再生・提供後の列を組む仕組み（§3の論点A・B） | 選択なしで「提供後が続く」仕組みを先に固める |

## 2. 現状（静的解析で確認済み）

### 2.1 客のイベント列
`Day1Events.customer_events(客id, mob_count, scene_id)`が、来店時（`DebugPanel._load_current_customer()`）にイベント列を**最後まで組む**。名前あり客の汎用の列は`[前回の2行(GREET)…, GREET(注文)…, ADJUST, SERVE, REACT, +_customer_extra_events]`。`REACT`は`reactions`（出来ごとに2パターンのプール）と`wanted_tags`・`favorite`・`servings`・`sale`を持つ。

### 2.2 REACTの受け側
`DebugPanel._apply_event`の`"REACT"`が、断る（`_pending_decline`）・モブの部分提供・鍋不足の保留・通常提供（`_serve_customer`）に分かれる。反応文は`_current_reaction_text()`が`reactions[出来]`のプールから`reaction_variant`で1つ選んで**表示するだけ**（`REACT`のあとにイベントを足してはいない）。REACTの後に続くのは`_customer_extra_events`（新人警官の共通会話と会計は`_OFFICER_AFTER`・`_OFFICER_PAYMENT`の仮定数、チンピラの場所代`PAY`）。

### 2.3 EventRunner
`events`配列を`index`で進める使い捨て部品。`options`を持つイベントは入力待ち。**「新しくcurrentになったイベントに効果を一度だけ適用し、index 0は適用されない」**という既知制約がある（`CURRENT_SPEC.md`§4）。実行中に`events`へ挿入・追記する前例は、PREPの`prep_after_tier_events`の差し替えなど（`runner`ごと差し替える形）。

### 2.4 来店記録
`customer_memory[id] = {favorite_known, visits:[{day, slot, served, grade, grades, ingredients, episode_id}], facts:{}, seen_episodes:[]}`。`facts`には`CustomerMemory.set_fact`／`fact`の手段だけがある（`requires.facts`が読む）。`visits`に`request_honored`・`choices`は無い（`DESIGN.md`10.8.5では予定）。

### 2.5 提供しない経路
断る（`_serve_customer_decline`）・提供できず退店・早仕舞い（`_auto_close_kitchen`ほか）・到着前に閉店して来なかった客、がある。到着前に閉店した客は来店記録を作らない（4-4b-1）。

## 3. 決めてほしいこと（planで方針を示す。迷う点は選択肢を並べて推奨を添える）

**論点A：提供後の列を組む方式（核心）。** 反応・本文・締めは「実際の出来と選択が出た後」に組む（10.8.6）。現状は来店時にイベント列を最後まで組んでいる。次を比べて推奨を示すこと。
- (1) REACTの処理後（`_serve_customer`の最後）に、`Day1Events.after_serve_events(客, 場面, 出来, 来店記録)`で提供後の列を組み、`flow.runner.events`の現在位置の後ろへ**差し込む**（`_customer_extra_events`の`PAY`・共通会話との順序を決める）。
- (2) 来店時に「提供後のスロット」（種類だけを持つ空きイベント）を置き、REACT後に中身を解決して置き換える。
- (3) 提供後は別の`EventRunner`へ切り替える。
- いずれの場合も、EventRunnerの既知制約（index 0・新しいcurrentにだけ効果が適用される）と整合すること、再挑戦（4-1）・保存（朝にだけ保存。会話の途中では保存しない）と矛盾しないこと、`Forecast`・杯数先読み（`customer_events`を何度も呼ぶ）に副作用が出ないこと（組み立ては状態を読むだけで書かない）を確認する。
- 今の`_current_reaction_text()`（反応文を表示するだけ）との関係。反応を`TEXT`イベントとして流すのか、今の表示を維持するのかを決める。**既存21場面の画面表示とイベント列を変えない**ことが条件。

**論点B：`UNSERVED`と提供しなかった経路。** 断る・提供できず退店・早仕舞いのとき、`reactions.UNSERVED`を出す。
- 経路ごとに、どの時点で`UNSERVED`と`body`（未提供版）を再生するかを表にする（断る／鍋不足で退店／閉店時に列に残っている客／到着前に閉店して来なかった客）。
- `must_info`を持つ場面は、提供しなかったときも本文を再生する（10.5.5）。持たない場面は、提供しなかったとき本文を再生するかどうか（既定：再生しない＝反応のみ）を決める。
- **到着前に閉店して来なかった客**の場面を再生するか。10.5.5の「早仕舞いでも未提供版で再生」を文字どおり読むと再生が要る。再生するなら閉店処理のどこで差すか、しないなら`must_info`をどこで担保するか（ニュースが担う前提？）を示す。推奨が決められなければ「確認事項」として挙げる（しまさんに確認する）。
- 提供しなかった客で`facts`を立てるか（推奨：本文を再生しない限り立てない。理由を示す）。

**論点C：選択（`choices`）。** 店主の距離感の選択は二択（10.5.4）。善悪点にしない。
- データ形：10.8.6の例`[ { "id": "message", "options": [ { "label": "預かる", "set": { "holding_message": true } }, { … } ] } ]`を基本とする。1場面の選択の数の上限（推奨：1〜2）。
- 画面：`options`を持つイベント（入力待ち）として出す（`EventRunner`の既存の仕組み）。仮UI（`DebugPanel`のボタン）でよい。本番UIはフェーズ6。
- 選んだ結果を来店記録の`visits[今日].choices`（`{choice_id: option_id|label}`）と、`set`の事実として`facts`へ残す。`set`が`facts`に書くキーと`sets_facts`の関係（重複・上書きの順序）を決める。
- **選択を押さない・断った客は選択を出さない**。説明のない大きな罰を起こさない（10.5.4）。選択は料金・評判・評価を変えない。
- 選択の出す位置：`body`の途中か、`body`の後か。推奨を示す。

**論点D：締め（`closing`）。** 選択・約束に応じた短い差分。
- データ形の候補：`{ "default": [...], "<choice_id>:<option_id>": [...] }`のように、選択の結果をキーにした単純な引き当て。**式やスクリプトは持たない**。該当が無ければ`default`。
- 提供の出来（4段階）で締めを分けるか（10.5.3は「差分は冒頭2行・反応・締めだけ」。締めは選択・約束に応じる、が基本）。出来では分けない案を推奨するが、判断を示すこと。
- 謝罪などで評価は変えない・わざと失敗すると親密になる経路を作らない（10.5.3）。コードで担保できる部分（出来の評価は`judge_bowl`のみが決める等）をテストにする。

**論点E：事実（`sets_facts`）と来店記録の拡張。**
- `sets_facts`：場面が終わったときに`facts`へ書く。**1場面につき1〜2個まで**（10.8.5）。データ検証テストで上限を守らせる。書く時点（本文を再生し終えたとき。提供しなかった場合は書かない、が推奨）。
- `visits[].request_honored`：今日の頼みに応えたか。`order.today_request`がある場面だけ、実効注文の2タグが両方一致したら`true`（=GOOD以上の一致）など、定義を決める。今日の頼みが無い場面は項目を入れない（推奨）。
- `visits[].choices`：論点C。
- **保存**：来店記録は`SAVED_FIELDS`に入っていて朝に保存される。`visits`の要素にキーが増える。任意キー（無くても読める）として版を上げないか、版6に上げるかを推奨付きで示す。`MorningSave.is_valid()`の型検査も合わせる。再挑戦（朝へ戻す）で選択・事実が正しく戻ることをテストにする。

**論点F：`pre_order`と`must_info`。**
- `pre_order`：前回の2行と注文（`greet`）の間に出す行（任意）。無ければ何も出さない。
- `must_info`：印の読み取りだけ（`ScheduleData.episode_must_info`）。9項目の管理（ニュースとの突き合わせ）は次のD（日別ニュース）で扱う。ここでは「印があれば、提供しなかったときも本文を再生する」（論点B）に使う。

**論点G：複数杯の場面（配達員の3杯列）。** Day1配達員の「1杯ずつ3回」（`_delivery_man_events()`・`THREE_CUPS_EPISODE`）は、10.8.6では「複数杯の場面」として表すことになっている。**この依頼では実装しない**（動かさない列）。ただし、planで次を答えること：Cの`reactions`・`body`・`closing`の形が、将来「杯ごとの注文・杯ごとの反応・持ち帰りの杯（判定のみ・反応なし）」を表せる形になっているか、拡張するときに破壊的な変更が要らないか。

**論点H：自動試遊と既存テストへの影響。** 既存データでは動作が変わらない。試遊が新しい操作（選択など）を前提にしていないか、選択のボタンが試遊の進行を止めないか（ハンドラ直呼び）を確認する。書き換える既存テストと理由の一覧を出す。

## 4. 新規テスト（最低限）

- **提供後の列**：テスト用の場面で、GREAT/GOOD/OK/BADそれぞれ「反応 → 本文 → （選択）→ 締め」が期待の順で再生される。キーを持たない場面は従来と同一（イベント列・画面表示が一致）。
- **UNSERVED**：断る・提供できず退店・早仕舞いのそれぞれで、論点Bの表どおりに反応と本文が出る／出ない。`must_info`ありの場面は本文が出る。
- **選択**：選択が来店記録の`choices`と`facts`に残る。選択前後で料金・評判・評価・鍋・在庫が変わらない。締めが選択に応じて変わる。該当が無ければ`default`。
- **事実**：`sets_facts`が1〜2個の上限内で書かれる（上限超えのデータは検証テストで落ちる）。書く時点（論点E）の確認。次の朝の`EpisodeSelector`が`requires.facts`でその事実を読んで別の場面を選ぶ（フィクスチャ）。
- **副作用なし**：`customer_events`・`after_serve_events`を何度呼んでも状態が変わらない。`Forecast`・杯数先読みの結果が変わらない。読んでいる間に鍋・腐敗・客の待ちが進まない。
- **保存**：論点Eの結論どおり（版・往復・再挑戦で選択と事実が戻る）。
- **データ検証**：場面データの新しいキー（`body`・`choices`・`closing`・`sets_facts`・`pre_order`・`must_info`）の型検査（`tests/episode_data_test.gd`）。実データ21場面は上のキーを持たないこと。
- **自動試遊（3シード×13方針）が4-3の結果と完全一致**（日別・現金・評判・インシデント・結果画面の集計まで差分0）。

## 5. 注意

- **既存データのままなら動作を変えない**。差が出たら原因を調べて報告すること（数値は調整しない）。
- 範囲外：本文・選択肢・締めの**文面**（脚本。4-5・4-8）、ニュースの仕組み（D）、レシピ保存・会話ログ・既読スキップ（B）、修繕基金（A）、複数杯の場面への置き換え（論点G。動かさない）、`_OFFICER_AFTER`・`_OFFICER_PAYMENT`のデータ化（脚本の段階）。ただし、論点Aの方式を決めるために、これらの定数との順序は考慮すること。
- 好感度のような数値は持たない。評価・料金・評判・関係を選択や本文で変えない。乱数を使わない（反応の2パターンの抽選は既存の`reaction_variant`のまま）。
