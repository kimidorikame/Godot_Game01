## 2. 現行コードで確認した事実（planの前提）

- `Ledger.CATEGORIES`に`"fund"`が**宣言済みだが未使用**（`scripts/ledger.gd`）。`Ledger.record(category, amount, item, count, unit_price, ref)`は支出を**負額**で積む。
- `Result.repair_paid(ledger)`（`scripts/result.gd`）は`fund`の支出（負額）の合計を正の値で返す。`Result.summarize`が`repair_paid`と`cash_plus_repair`（＝現金＋修繕額）を作り、`judge_goals`は`cash_plus_repair`で判定する。**この形は変えない**（`tests/result_test.gd`が`fund`80で検証済み）。今は`fund`を記帳する処理が無いので常に0。
- `Ledger.usable_cash()`＝所持金−今日の確保額。`GameState.try_pay(amount)`で所持金から引ける。
- **運営費は朝のWAKEに入った瞬間に必ず払う**（`debug_panel.gd`の`_pay_or_game_over(GameState.DAILY_OPERATING_COST, "daily_cost")`。払えなければゲームオーバー）。徴収日（`GameState.is_collection_day()`。`week7`では`bills`の`days:[1]`）は場所代・水道代も絡む。したがって**CLOSEで積みすぎると翌朝の運営費が払えずゲームオーバーになりうる**。これが本書最大の注意点（§3 Q3）。
- 朝の保存（`MorningSave`）は`ledger`を含む（`morning_save.gd`の保存項目に`"ledger"`、検証は66行付近）。基金の記帳は帳簿の1行なので**保存の版は上げない見込み**（planで確認すること。検証が`category`を限定していないか）。再挑戦・続きからは「朝」へ戻すので、**その日のCLOSEで積んだ分は、同じ日の朝へ戻すと消え、翌朝以降へ進んだ場合は残る**。
- CLOSEの語りは`Day1Events.close_events()`のTEXT3つ（最終日は「（終了）」を追加）。`_set_runner_for_phase(CLOSE)`が、理由・未提供の退店・共通イベント（System D）を前に付けて組む。**この列は変えない**（変えると既読・ログ・試遊のTEXT数が動く）。
- 日別の成績文は`_on_day_ending()`（NEXT_DAY→WAKEの折り返しで呼ばれる）が`log_entry`を作り、`_format_day_summary(log_entry)`が整形して翌朝の先頭に出す。`spend_by_category`は`Ledger.spend_by_category_today()`をそのまま持つ。**CLOSEで積んだ基金は、この時点で当日の帳簿に入っている**ので、`closing_money`（基金を引いた後の所持金）にも`spend_by_category`の`fund`にも自然に反映される。`_format_spend_by_category`の固定カテゴリ表には`fund`が無いので、足す必要がある。
- 結果画面は`Result.format_report`（1枚目）が`現金: ＋ 支払済み修繕額: ＝`の行を既に出している。
- `Rules`は`week7.json`からの読み出し口（`recipe_slots()`等）。設定が無いキャンペーン・テスト用フィクスチャでは**既定値（機能オフ）で動く**形に揃える。
- 最終日（`GameState.is_final_day()`）はCLOSEの次がNEXT_DAY→RESULT。翌朝の運営費は発生しない。

## 3. 基金の仕様と、決めてほしいこと（推奨付き）

### 3.1 仕様（`DESIGN.md`10.7どおり。ここは変えない）

- 任意。強制しない。**積まなければ何も起きない**。
- 累計150／300／600で段階が上がる。**累計は帳簿（`fund`の合計）から導く**。専用の保存状態を新しく持たない。
- **返金不可**。引き出し・取り消しの操作は作らない。
- **売上・需要・評判・料金など、ゲームの数値を恒久的に変える効果は付けない**。段階で変わるのは「見た目と営業記録」＝表示のみ。
- 目標判定は`現金＋支払済み修繕額`のまま。投資しても現金目標が不利にならない。
- 仕入れと同じ現金（所持金）から払う。

### 3.2 決めてほしいこと

planで次の各項目に**番号付きの質問（Q）として推奨案を添えて**示すこと。

**Q1 積む時点**
- 推奨：**CLOSEの語りをすべて読み終えた後、NEXT_DAYへ進む前**だけ。その日の売上が入った後なので「今日入れるか、明日の仕入れに回すか」の判断になる。
- PREP・OPEN中は積めない（仕入れと同日に混ざり、上限の計算が複雑になるため）。
- 積む操作は任意で、何も押さずに[次のPhase]へ進めば「積まない」。**[次のPhase]の進行条件（ゲート）は変えない**。
- 自動閉店（鍋切れ・早仕舞い）でCLOSEへ来た日も同じ扱い。ゲームオーバーの日はCLOSEを経ないので積めない。

**Q2 積む額の選び方**
- 推奨：**固定の刻みのボタン**（例：25／50／100）。刻みは`week7.json`に置く。1日に何回押してもよい（その都度1行ずつ帳簿に積む。上限の範囲内）。
- 任意の数値入力欄は作らない（仮UIが重くなる）。
- 「次の段階まで」ボタンは、あっても追加の便宜に留める（planで要否を判断）。

**Q3 積める上限（安全上限）**
- 推奨：`積める額 ≦ 使える現金（Ledger.usable_cash()）− 翌朝に必ず払う額 − 翌日の最小仕込み額`。
  - 翌朝に必ず払う額＝運営費＋（翌日が徴収日なら場所代・水道代）。**今日が最終日なら翌日が無いので0**。
  - 最小仕込み額＝`Rules.prep_tiers()`の最小段階の価格（week7では80）。「積んだせいで翌日に何も仕込めず詰む」を防ぐための下限。
  - 今日が最終日なら翌日が無いので、**上限は所持金そのもの**（運営費・仕込みの下限は不要）。
- 上限を超える額のボタンは押せない。**基金の操作でゲームオーバーになる経路を作らない**（テストで確認）。
- 翌日の徴収日判定は`GameState.is_collection_day()`が「今日」しか見ないため、「指定日の徴収額」を返す補助が要る。重複した実装を作らず、既存の`Rules.bills()`の読みを使うこと。
- 異論があればplanで代案を示してよい（例：最小仕込み額を含めない）。

**Q4 累計の上限**
- 推奨：最終段階（600）に達したら、それ以上は積めない（無駄に現金を減らさないため）。表示は「完了」。

**Q5 見た目・営業記録の反映先（仮UI）**
- 推奨（すべて**表示だけ**。数値を変えない）：
  1. 積んだ直後、積み立て行に現在の段階名と累計、次の段階までの残りを出す。段階が上がった瞬間は、その旨の一行（仮文面）を行の近くに出す。
  2. **翌朝の成績サマリー**（`_format_day_summary`）に、基金を積んだ日だけ「屋台: 手書きの看板（修繕 累計150）」のような1行と、支出内訳に「修繕基金NN」を足す。積まなかった日の文面は**現状と1文字も変えない**。
  3. **結果画面の1枚目**（`Result.format_report`）に、累計が1以上のときだけ屋台の段階を示す行を足す。累計0なら**現状と同一**。2枚目（目標）・3枚目（物語欄）は触らない。
  4. STATE VIEWERに、基金の累計と段階を表示する行（機能が有効なときだけ）。
- 段階名と一行の文面は`week7.json`の`repair_fund.stages`に置く（**仮文面**であることをコメントかnoteで明示。後で差し替えられるように）。
- CLOSEの`close_events()`のTEXT列には**足さない**（既読・ログ・試遊に影響するため）。

**Q6 記録するデータ**
- 推奨：`log_entry`（`balance_log.jsonl`の1日分）に**新しいキーを足さない**。基金の額は`spend_by_category`の`fund`と帳簿から導けるため、二重の集計を作らない。足す場合は「追加のみ・既存キー不変」を守り、`playthrough_results_regulars.json`との比較に影響しないことをplanで示すこと。

**Q7 自動試遊**
- 既存の13方針×3シード＝39本は**一切変えない**（基金を操作しないので結果は同一のはず）。
- 任意：基金に積む方針（`DESIGN.md`10.13にある「修繕基金に積む」）を**別枠**で追加し、39本の比較とは別の結果ファイルへ出す。目的は「積んでも目標判定（現金＋修繕）が不利にならない」ことの傾向を見ること。数値の調整は依頼しない。追加する場合は別コミットにし、既存方針の結果が動かないことを確認する。

**Q8 設定が無い場合**
- `repair_fund`が無い（または空の）キャンペーン・テストでは機能オフ：積み立て行を出さず、サマリー・結果・状態表示も現状のまま。これで既存フィクスチャ・テストが無改修で動くことを確認すること。

### 3.3 設定データの形（提案）

```json
"repair_fund": {
  "steps": [25, 50, 100],
  "stages": [
    { "id": "sign",  "total": 150, "label": "手書きの看板",     "note": "（仮）" },
    { "id": "shelf", "total": 300, "label": "棚と雨よけ",       "note": "（仮）" },
    { "id": "owner", "total": 600, "label": "屋台を自分の名義に", "note": "（仮）" }
  ]
}
```

- 数値（刻み・累計の境目）をコードに直書きしない。
- 形はplanで変えてよい（段階を増減できること、`total`が昇順でない・刻みが0以下などの不正値を安全に無視または拒否できること）。

## 5. テスト（最低限）

新規スイート（例：`tests/repair_fund_test.gd`）と既存テストの更新。**スイートの最後は`return c.finish()`**。

1. **段階の境目**：累計0／149／150／299／300／599／600で段階が正しい。次の段階までの残りも。
2. **積む処理**：所持金が積んだ額だけ減り、帳簿に`fund`が負額で1行増え、`Result.repair_paid`がその合計になる。複数回で累計が加算される。
3. **上限（Q3）**：上限ちょうどは積める／1超えると積めない。徴収日の前日、最終日、確保額がある場合。積んだ後に翌朝の運営費が**必ず払える**こと。上限いっぱいまで積んでも翌日の最小仕込みが買えること。
4. **拒否される場合**：CLOSE以外のフェーズ、機能オフ、刻みに無い額、0以下、最終段階到達後。いずれも所持金・帳簿が変わらない。
5. **目標判定**：積む前後で`Result.summarize`の`cash_plus_repair`が（他の取引が無い限り）変わらない。`judge_goals`の結果が積んだだけで不利にならない。
6. **効果が無いこと**：積んでも、所持金・帳簿以外の状態（評判・需要・料金・在庫・今日のplan）が変わらない。
7. **保存**：朝の保存→復元で帳簿の`fund`が残る。同じ日の朝へ戻すとその日に積んだ分が消える。保存の版が変わらない（版を上げる場合はその理由）。
8. **サマリー・結果**：積んだ日だけ翌朝サマリーに屋台の行と「修繕基金NN」が出る。積まなかった日の文面が現状と同一。結果画面は累計0なら現状と同一、1以上なら段階の行が出る。
9. **機能オフ**：`repair_fund`の無い設定で、積み立て行が出ず、既存の全テストが通る。
10. **自動試遊**：3シード×13方針が`playthrough_results_regulars.json`と**39/39完全一致**（全キー差分0）。
11. **既存テスト**：文面の厳密一致を検査しているテスト（`_format_day_summary`・結果画面）が、基金0のとき**無改修で通る**こと。直す必要が出たら理由を報告に書く。
