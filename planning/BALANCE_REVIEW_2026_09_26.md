# 夜湯：経営QA・数値案・会話に頼らない遊びの提案

2026-09-26。対象は GitHub / ローカルで照合した **`1eadb70155e4d614466bfd5003d10b65be6bb3bb`**。添付のパラメータ一覧は資料として照合し、そこに書かれた「現行仕様」を検証結果と同一視しない。ゲーム本体の修正は行っていない。

## 1. 採用判断

**7日版の骨格は、売価45・初期現金600・日費用80・仕込み8/11/14杯・水2回・最上帯71を推奨する。** 単に前案を引き継いだ判断ではなく、売価40/50、日費用70/90/100も比較した。まず直すべき点は、初日の需要・初期在庫の扱い・料理の販売成立条件である。

現在の実装は、客足予報と嗜好の多様化により、旧版より仕入れを考えられる状態になった。一方で「何も入れずに45で売る」「初日だけ旧来の大量無料在庫と13杯の注文が残る」ため、前案の平均現金や目標をそのまま当てはめられない。

本書の「推奨値」は試遊へ進めるための基準であり、あらゆる人に最適な値を証明したものではない。数値の成立と、面白さの実証を分ける。

## 2. 何を検証したか

- **実ゲーム**：対象コミットを `git archive` で固定したコピーで、DebugPanelの操作ハンドラ、EventRunner、GameState、実際の客JSONを動かす7日通し自動プレイ。7方針×シード1〜30。市場で代金を払う。通しプレイへの所持金・材料の付与は行わない。
- Day2以降、予報を読む方針は最新版SNSに公開されている当日の客・人数・要求・判明済み好物だけを仕入れに使う。翌日の抽選を読まない。Day1だけは実際の13杯を既知として仕込みを選び、持ち帰り注文も仕様を既知として対応するため、完全初見の試験ではない。
- 毎朝 `seed(run_seed * 1000 + day)` で乱数を設定。反応文の抽選で翌日の需要乱数がずれないようにした。評判が違えば同じシードでも人数は変わる。
- 既存テストは**10スイート・597項目で失敗0**。境界値の再現は別スクリプト。全在庫のADJUSTを1280×720で実描画し、画面を確認した。
- **提案の数値**：有料初日セット210・初日9杯・固定の常連日程・人数幅の予告を持つ別の設計モデルを使用。28条件×1000シード＝**28,000回**。現行Godot版の再現モデルではない。
- 実行エンジンはローカルで利用できた **Godot 4.4.1**。`project.godot` のfeaturesは4.7表記なので、配布に使う4.7での最終検証は別途必要。Windows証明書ストアへのアクセス警告と、既存テストが意図的に読む不存在JSONのエラーは、今回の経営計算の失敗とは区別した。

実プレイの集計は [playtest_2026_09_26/PLAYTHROUGH_RESULTS.md](playtest_2026_09_26/PLAYTHROUGH_RESULTS.md)、生データ・再現方法は同フォルダに保存。自動操作の比較であり、人が触って面白さを評価したユーザーテストではない。

## 3. 現行版の懸念点と優先度

### P1：具材ゼロでも満額販売でき、低品質営業が資金面で成立する

ADJUSTで何も選ばずに提供するとBADになるが、売上は通常どおり45。モブも選択素材が空のまま達成可能人数を計算できる。最低評判でも6〜8杯の需要が残るため、材料を買わず小仕込み80＋運営費80だけで、平均7杯×45−160＝**155/夜**の現金を得られる。鍋の濃さ・供給で変わる場合はあるが、最低需要帯では8杯仕込みで足りる。

再現：通常の新規ゲームから、具材を選ばず「入力完了」→団体なら人数確定→提供を続ける。通し試験の `bare_broth` が該当する。根拠：`scripts/debug_panel.gd` の `_apply_mob_recipe()` / `_serve_customer()`、`scripts/open_controller.gd:196`。

**対応案**：販売成立には「味素材1つ＋具素材1つ」「濃さ1〜5」「提供分の残量」を必須にする。持ち帰りの `judge:false` でも販売成立条件は共通にする。未選択は未完成として、材料・鍋・現金を動かさず不足を表示。注文拒否は別の操作にする。無言の客にも同じ条件を適用する。

BADの全額返金も別モデルで比較したが、品質失敗2件の平均現金は1495→1282、1500達成率は49.2%→0.6%へ低下した。この「2件」は個人1杯と団体1組であり、2杯ではない。**全面返金を空料理対策と同時に入れる案は推奨しない**。まず未完成料理だけを販売不可にする。誤った味の完成料理が必ず倒産を招く必要はないが、低品質を続ける方針が良質な営業より現金・品質・常連実績のすべてで有利にならないかを再検証する。

### P1：初日の需要9杯という定数と、実際の13杯が一致しない

`GameState.total_demand_today()` は9。しかしDay1は需要配分処理を通らず、配達員3杯＋モブ4杯＋チンピラ1杯＋モブ4杯＋老婆1杯＝**13杯**。小仕込みは給水2回でも12杯しかない。さらに初日は全店舗が閉まっており、だしは0、購入もできない。

中仕込み11杯では、明け方より前に12杯の注文があるため、途中で水を足すと濃さ1になり、だしで補正できない。初見の「適量と思って中を選ぶ」が品質低下へつながる。大14杯なら水なしで供給できるが、予報の「配達員」に3杯と書かれていないため、判断根拠が不足する。

**対応案**：初日のモブは2人ずつ、夜半は安宿受付固定とし、総需要9杯へ揃える。配達員には「本人2杯＋持ち帰り1杯」を明示。Day1専用の需要定数・実注文・予報・テストを同じデータから集計する。13杯を意図して残す場合は初日大仕込みを案内し、初期在庫と経済モデルを13杯で再計算する必要がある。本書は学習量の少ない9杯を推す。

根拠：`scripts/game_state.gd:57` / `:63`、`scripts/day1_events.gd:328` / `:465`、`scripts/debug_panel.gd:1695`。既存テストも13杯を期待しており、テスト成功は提案との一致を意味しない。

### P2：支払い予定が未払金と一致しない

初日起床直後は600−80＝520。表示は「支払い予定170」だが、そのうち80は天引き済みで、今後払う場所代90＋水道代50＝140とも一致しない。二重請求ではないが、予算の表示として誤解を誘う。

**対応案**：「残金520／今日の未払140／仕込み・仕入れに使える380」と表示。支払済み運営費80は別欄。新案では初日の140も朝に確保し、会話での支払い演出と帳簿を分ける。初日に市場で過剰購入して水道代が払えなくなる、という旧プローブは店舗のロックを無視した直接呼び出しだったため、通常操作の不具合としては採用しない。

### P2：鍋容量と評価ルールに、提案からの差が残る

- 現行は14杯の鍋へ水→だし→水を入れて、同時残量18杯にできる。**一夜の供給上限18**と**同時容量14**は別。14を採るなら `can_add_water()` に容量条件を加える。18を許すなら「同時容量14」という提案を撤回する。日次最大供給が無限になる問題ではない。
- 現行は味なしの豆腐＋肉団子でも、チンピラの既知好物によりGOODになる。新案では基本の味・具がそろった後だけ好物でGREATへ上げる。
- 現行の濃さ不適切＋傷みは合わせて1段階低下。前案は各1段階。この差は旧仕様の保持であり、偶発的バグとは断定しない。新案は各1段階とし、提供前に結果の低下要因を表示する。現在のように両方を1回の減点へまとめる方針を続けるなら、その条件でモデルも再計算する。

### P2：終盤の目的と再挑戦導線が不足する

Day7終了後に成績を固定して選ぶ画面がなく、次のPhaseでDay1へ戻る。GAME_OVERにもその朝からの再挑戦がない。7日目の好物投資は翌日の客数へ回収できないため、現金だけが目的なら合理的に削られる。

**対応案**：Day7で結果を保持し、「現金・修繕・GOOD率・常連の満足・未提供・廃棄」を表示して再挑戦を選ぶ。失敗時は同じ朝・同じ抽選で仕入れからやり直せる。無償の何度も引き直す抽選にはしない。

## 5. 会話なしで経営を面白くするMVPの変更

1. **朝の一画面で「需要・在庫・予算」を比較する。** 現在のSNS予報に、総杯数、必要な味具、今日使い切りたい数量、パック数・単価、支払確保後の現金を足す。上限仕入れと平均仕入れをプレイヤーが選べるようにし、自動で最適量を購入しない。
2. **作ったレシピを保存し、再注文を短くする。** お気に入り料理を選ぶ→材料・鮮度・提供人数を確認→出す。具不足時の代替や2レシピ分割は残す。文章の「次へ」と素材の連打を、難しさの中心にしない。
3. **一晩に小さな方針を1つ選べるようにする。** 例は「余りそうな食材で看板料理を1品掲示」。総需要を無条件に増やさず、その軸の客の割合を少し変える。次の夜だけの効果、予告された範囲内の変化に限定し、同じ安い料理だけへ永久固定できないかを見る。これは基準モデルには未導入のA/B試験案。
4. **ミスを次の朝の判断へつなげる。** 前日成績の「未提供2」は素材不足／鍋不足で分け、「廃棄32」は品目を出す。売上が多いのに現金が少ない理由を、買い残しと使用原価から読めるようにする。現行ログは廃棄額はあるが、使用原価・保有在庫価値が不足している。

作業化の確認は、同じ需要でも余り在庫や時間帯に応じて仕込みを変えるか、同じレシピの操作回数が減るかで見る。初見5人程度の短い試遊なら「Day3までに仕入れを変えた理由を説明できる4人」「同一注文の入力を30%短縮」「1〜2回の失敗からDay7まで営業継続できる」を仮の合格目安にする。これらはまだ人で計測していない。

## 6. 一律価格のリスクと対策

一律45自体は、安い食事を求める街に合う。問題は、安い料理だけの方針と高い好物への投資の回収が非対称で、客層の抽選で原価も動くこと。高級具の全員提供を正解にせず、基本GOODでも生活でき、好物で客数・関係・実績を選んで伸ばす構造にする。

- 未完成の料理は販売不可。品質評価の低さと、売り物として成立していないことを区別する。
- 無料初期在庫を付けるなら600との合計価値で難度を設計する。本案は初日セットを購入する方式に一本化。
- 初日固定・朝の予告・部分提供・同じ抽選でのやり直しを使い、金額以外でも運の影響を調整する。
- 海鮮組が重なる夜だけ難度が跳ねる場合は「7客種の袋から重複なしで抽選」をA/B比較する。TREATのモブは1種類なので1夜1組までになる。これは等確率独立抽選の基準モデルからの変更なので、採用前に再計算する。
- 濃さと鮮度の二重失敗を入れるなら、投入前に「このままだと2段階下がる」を見せる。難度を上げても、理由が見えない罰にはしない。
- 固定費80→90は後から選べる厳しめ設定にし、通常版で一度に複数の経済値を上げない。

## 7. スープとドラマを結び付ける案（2つ）

### A. 「いつもの注文」と「今日の事情」が食い違う夜

いつも辛い肉団子湯を注文する配達員が、今日は「明け方まで走るから胃に軽いのを」と頼む。会話を飛ばしても注文カードには「本日MELLOW＋GENTLE希望」と残す。保存した定番レシピをそのまま出すか、今日の事情へ合わせてココナッツ乳＋豆腐へ替えるかを選ぶ。配達員の好物が豆腐という設定も維持できる。基本要求を固定する7日版に対しては、将来の例外イベントとして扱う。

材料を替えたことが会話の切り口になる。「気づいてくれた」から近況を話す、いつもの味から昔話へ進む、という差にする。高級な3素材を出すことだけが話を進める鍵にならないようにする。核心の物語はBAD1回で永久に失わず、後日の再来店で拾える。

### B. 取り置きした一杯が、来ない誰かを待つ行為になる

客から「夜明けに2杯、包んでおいて」と頼まれる。受けると予報上の2杯を予約枠へ移し、同じ鍋と食材から確保する。途中の団体へ売れば今の売上は確実だが、取り置きを守れば最後の客との会話が変わる。

約束の人数は受付済み需要に含め、予約と通常注文で二重に売上を計上しない。約束を断ること自体は未提供として減点せず、受けた後の不履行だけを別記録にする。会話未実装でも「予約2／残量4／今の注文3」というカードだけで判断を試せる。将来は、その2杯の相手を会話で明かす。

## 8. 儲ける意味を作る仕組み（2つ）

### A. 屋台の修繕・所有化を、見える積立目標にする
