## 2. 現状（静的解析で確認済み）

### 2.1 `data/day_schedule.json`
日番号（"1"〜"7"）をキーに、3枠（宵の口・夜半・明け方）を持つ。各枠は`main`（固定）または`main_pool`（抽選。同日の重複を避ける）と、`mob`（false／true／`{"pool":[…]}`）を持つ。

|---|---|---|---|---|
| 1 | delivery_man | thug | granny | 明け方はモブなし。夜半のモブプールは3種（実際はday_overridesで固定編成が優先） |
| 2 | officer | プール3（granny/thug/delivery_man） | 同左 | |
| 3 | hooker | プール4 | プール4 | |
| 4 | streamer | プール5 | プール5 | |
| 5・6 | プール6 | プール6 | プール6 | 全抽選 |
| 7 | プール5（granny以外） | プール5 | granny固定（モブなし） | |

つまり常連のうち固定は一部だけで、Day2〜7の大半は抽選。10.5.1の固定日程（21枠）とは別物である。

### 2.2 `ScheduleData`（`scripts/schedule_data.gd`）
`day_schedule(day)`が日番号キーで引き、無い日は"1"へフォールバックする。ほかに`customer_data(id, day)`・`mob_data(id)`・`kit_data(id)`がある。`clear_cache()`はテスト用。

### 2.3 `Day1Events.customer_schedule()`（`scripts/day1_events.gd`、約375〜450行）
1. 各枠について`_pick_main(slot, chosen_mains)`で常連を決める（`main`があればそれ、なければ`main_pool`から`randi()`で抽選。同日の重複を除く）。
2. Day1は`Rules.day_overrides(1).mobs`の固定編成（宵の口：港湾労働者2、夜半：安宿の夜勤受付2）。Day2以降は総需要からメイン客の合計杯数を引いた分をモブ杯数として`_plan_mob_groups()`で組に配分し、`_pick_mob_type(slot)`でモブの種類を`randi()`抽選。
3. `_plan_mob_groups()`の組の置き場所は`_GROUP_SLOT_PRIORITY`（夜半→宵の口→明け方→宵の口）で決め打ち。その枠が「モブなし」なら夜半へ振り替え。
4. デバッグ上書き（`debug_mob_count >= 0`）は総需要システムを丸ごとバイパスして`_pick_mob()`を使う。

### 2.4 乱数
`_pick_main`と`_pick_mob_type`は`randi()`（グローバル乱数）。DayPlanは4-1で保存・復元されるので、固定にしても再挑戦の同一性は変わらない。

### 2.5 その他の参照
`Forecast`（朝の一画面）は`GameState.today_plan["slots"]`を読む。`week7.json`の`forecast.regulars: "base_order"`は、客の基本注文を朝に出す設定。`tests/schedule_test.gd`・`tests/reputation_demand_test.gd`が`day_schedule`のデータ（枠数・プール）を直接見ている。

## 3. 決めてほしいこと（planで方針を示す。迷う点は選択肢を並べて推奨を添える）

**論点A：`week7_regulars.json`の形式。** 10.5.1の表をそのまま21枠として持てる形にする。案：
```json
{ "days": { "1": [ {"slot":"宵の口","regular":"delivery_man"},
                   {"slot":"夜半","regular":"thug"},
                   {"slot":"明け方","regular":"granny"} ], ... } }
```
- 枠名（宵の口・夜半・明け方）は現行の`name`と一致させる。
- 後の4-4で`episode_id`、4-6で街の動きを足せるよう、辞書の枠にしておく（今は`regular`だけでよい。4-4の項目を先取りしない）。
- 10.5.1の表を機械的に検証できる形にする（来店回数：配達員4・チンピラ4・新人警官4・老婆3・夜の女3・配信者3＝21、同日の重複なし）。このチェックをテストにする（論点Eを参照）。

**論点B：`mob_rules.json`の形式。** 「既定＋日別の上書き」（10.8.1）。案：
- 既定：モブの種類プール（現行の7種）と、枠ごとの可否（宵の口・夜半＝可、Day7明け方・Day1明け方＝不可）。
- 日別の上書き：日・枠ごとの可否やプール。
- Day1の固定編成は`week7.json`の`day_overrides."1".mobs`が優先する現行の仕組みをそのまま残す（本手順では動かさない）。
- 現行のDay1夜半`mob.pool`（3種）は、Day1では参照されない死データである。`mob_rules.json`へ移すときに残すか捨てるか、planで示すこと。

**論点C：`Rules`／`ScheduleData`のAPI。** `week7.json`の`regular_schedule`（"week7_regulars"）から`data/schedules/<id>.json`を読む。`ScheduleData.day_schedule(day)`を、新しい2ファイルから組み立てた**同じ形**（`{"slots":[{name, main, mob}…]}`）で返す互換層にするか、`customer_schedule()`を直接書き換えるか。**推奨は前者**（`customer_schedule()`・`Forecast`・`DayPlanner`・既存テストの変更を最小にする）。ただし、互換層を残す場合の寿命（いつ消すか）をplanに書くこと。

**論点D：旧`data/day_schedule.json`の扱い。** 新ファイルに完全に置き換わるなら削除する。残す場合は理由を書く。フォールバック（"1"へ戻す）はDay8以降のみに使う想定。

**論点E：乱数の変化と回帰確認。** 常連が固定になると、常連の抽選（`_pick_main`の`randi()`）が無くなり、モブ抽選の`randi()`の呼び出し順がずれる。結果として**自動試遊の数値は`daily65`と一致しなくなる**（常連の顔ぶれが変わる＝仕様変更）。したがって回帰は「完全一致」ではなく、次の確認にする。
- 3シード×13方針が完走し、進行停止が0であること。
- 平均最終現金・1500達成率・GOOD以上率が10.13の合格ラインの範囲内か（3-8の結果と比較して報告）。
- **数値（運営費など）は調整せず、結果をそのまま報告する。** 合格ラインを外れた場合の調整は、このチャットで判断する。

**論点F：常連の杯数。** 固定日程では「どの日にどの常連が何杯か」が決まる。総需要からメイン客の合計杯数（`_customer_total_servings`）を引いたものがモブ杯数なので、常連の杯数が日によって変わると、その日のモブ杯数も変わる。`customer_data(id, day)`が日番号でフォールバック（"1"）する点も含め、**21枠のそれぞれで、常連の杯数・注文・好物・会話が存在するか（フォールバックに落ちないか）**を一覧にして確認すること（10.5.1に「配達員（3杯）」とあるのはDay1のみ）。足りない（フォールバックに落ちる）組み合わせは報告し、データの補充は4-4・4-8の範囲として扱う。
