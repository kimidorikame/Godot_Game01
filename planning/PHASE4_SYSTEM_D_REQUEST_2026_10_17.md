## 3. 決めてほしいこと（planで方針を示す。迷う点は選択肢を並べて推奨を添える）

**論点A：ニュースのデータ形。** `data/news/week7.json`。基本案：

```json
{
  "id": "week7",
  "days": {
    "1": { "news": [ { "id": "n1", "headline": "…", "body": ["…"], "must_info": ["strike_started"] } ],
           "dm":   [ { "from": "市場の顔なじみ", "text": "…" } ],
           "events": [] },
    "6": { "news": [ … ], "dm": [ … ],
           "events": [ { "id": "clash_fire", "at": "夜半", "lines": ["…"], "must_info": ["clash_fire"] } ] }
  }
}
```

- **日番号をキーにする**ことになるが、DayPlan・`Rules.day_overrides`と同じ流儀（キャンペーンのデータが日を指す）なので問題ないか、`DESIGN.md`10.9の「日番号の直書きの置き換え」の趣旨（コードに日番号を書かない）と矛盾しないことを確認して示す。
- 必須情報の識別子（9項目）を決める（例：`strike_started`・`checkpoints`・`nightlife_spillover`・`video_spread`・`night_removal`・`rights_shift`・`clash_fire`・`official_arson_claim`・`truth_unresolved`）。識別子の一覧の置き場所（`data/news/`の中か、`week7.json`か）を示す。
- DM（市場の顔なじみなど）をニュースと同じ枠で持つか、別キーにするか。ニュースタブでの見せ方（ニュース／DMの区別）を示す。推奨を添える。
- 本文（文面）は**仮案を`SEVEN_DAY_OUTLINE.md`の表からそのまま入れ、仮データであることが分かるようにする**（例：`"provisional": true`）。実データでも9項目の担保テストが走るようにするため。文面は後から差し替えるだけで済む形にする。7日分すべてを埋める必要は無く、必須情報を載せる日（Day1〜7）に最低限のニュースを置く。

**論点B：朝に「必ず」提示する経路。** 「ニュースタブを開かなければ読めない」では必須情報が届かない。次を比べて推奨を示す。
- (1) WAKEのイベント列に、その日のニュースの見出しを`TEXT`として必ず差し込む（「スマホを見る。」の前後）。ニュースタブは、これまでの日の分も含めた読み返し用。
- (2) スマホを開くのを促すだけで、ニュースタブで読む形にする（強制しない）。
- (3) その他。
- (1)を採る場合、WAKEのイベント列が変わる（先頭に効果Eventを置かない制約＝`EventRunner`の既知制約）ことへの対処、日次の成績表示（前日の成績を先頭に出す`TEXT`）との順序、再挑戦（朝に戻す）で同じ表示になること、ゲームオーバー後の再開・新しい周での扱いを示す。
- 自動試遊が影響を受けないこと（WAKEの`TEXT`を進めるだけ）を確認する。

**論点C：共通イベント（必須情報#7、Day6の衝突と火災）。** 客の抽選に依存せず必ず起きる出来事。
- 原案：「時間帯切り替えテキストの差し替え＋その日だけのTEXT Event」（`SEVEN_DAY_OUTLINE.md`§8）。夕方に衝突（朝のニュースの続き）、夜に倉庫火災。
- 論点Aの`events`（日ごとの共通イベント。`at`＝出す時点：朝／宵の口の始め／夜半の始め／明け方の始め／閉店後 など）を使う案を基本とする。出す時点の候補と、それぞれの実装箇所（時間帯移行・CLOSE・WAKE）を表にし、推奨を示す。
- 共通イベントは**ゲームの数値（所持金・評判・在庫・需要・客の構成）を変えない**（演出を挟むが調理ループは壊さない）。数値に触れる日別の変化（市場の閉鎖＝海鮮が閉店、在庫の破棄など）は**範囲外**（§5）。
- 「早仕舞い」で閉店してしまった日でも共通イベントが届くか（出す時点が営業中だと、早仕舞いで届かない）。必須情報#7は、**早仕舞いでも届く**ことを担保する（例：閉店処理で未再生の共通イベントを再生する、朝のニュースに予告を置く、など）。方式を示す。

**論点D：必須情報の担保とデータ検証。**
- 9項目それぞれについて、「ニュース」または「共通イベント」のどこで届くかを`must_info`の識別子で結びつける。**客の場面（`episode.must_info`）は補強であり、担保の根拠にしない**（客が来ない・断る・早仕舞い・モブ0人でも届く経路が必要）。
- データ検証テスト：(a) 9項目の識別子がすべて、ニュースまたは共通イベントのどこかに現れる。(b) 現れる日が`SEVEN_DAY_OUTLINE.md`の表と一致する（日の対応を定数で持つか、データから検査するかを示す）。(c) 場面データの`must_info`の識別子が、9項目の一覧に存在する（未知の識別子を弾く）。(d) 客・モブ・評判に依存する経路だけで担保されている項目が無い。
- 「#9 真相は確定しない」のような、Day7全体にまたがる項目の担保の仕方（Day7のニュースに複数の説を並置し、どれも断定しない文面をデータで持つ。検証は「Day7のニュースに`truth_unresolved`の印がある」まで）。

**論点E：ニュースタブの表示。**
- `_format_phone()`の`"news"`を実データにする。表示：今日のニュース・DM、これまでの日の分（読み返し）。
- 日をまたいだ読み返しは**その周の既に過ぎた日と今日の分だけ**（未来の日は見せない）。再挑戦で朝に戻したとき、戻した朝より後の日の分は見えない。
- 既読の管理（読んだ・読んでいない）は**この依頼では持たない**（レシピ保存・会話ログ・既読スキップの手順Bで扱う）。保存する状態を増やさない方針を推奨するが、必要なら理由を示す。
- 本番UIの作り込みはフェーズ6。仮表示でよい。

**論点F：保存・再挑戦・新しい周。**
- ニュースは日番号から引く静的データなので、新しく保存する状態は無い想定。保存の版は上げない。共通イベントを「再生済み」と覚える必要があるか（同じ日に二重に出さない）、あるなら実行時の値で足りるか（保存しない）を示す。
- 再挑戦（朝へ戻す）でニュース・共通イベントが正しく再生されること、続きから読み込んだ朝で同じ表示になることをテストにする。

**論点G：自動試遊と既存テストへの影響。** ニュースの提示は表示だけなので数値は変わらない。WAKEのイベント列が変わる場合の影響（試遊がWAKEの進行を`TEXT`のスキップで進める作りか）を確認し、書き換える既存テストと理由の一覧を出す。

- **ニュースタブ**：今日の分と過去の日の分が出る。未来の日は出ない。再挑戦で戻した朝より後の日は出ない。
- **保存**：論点Fの結論どおり（版・往復）。
- **自動試遊（3シード×13方針）が4-3の結果と完全一致**（日別・現金・評判・インシデント・結果画面の集計まで差分0）。
